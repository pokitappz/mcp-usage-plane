Security

What this service holds, what it cannot hold, and what it does not yet do.

A trust page made of adjectives is worth nothing. This one is specific, it names the mechanisms, and it ends with the limitations, because a page that lists only strengths tells you the author was selling rather than describing.

The ledger

Seven columns. None of them can hold your customers' content.

A usage event is an identifier, an account, a customer identifier, a meter label, a count of units, and two timestamps. That is the whole row. There is no column for a tool name, a prompt name, a resource URI, an argument, or a result, so none of them can be stored here even by mistake.

The two strings are yours: customer_id and meter are whatever your sidecar sends. Send an opaque identifier and a meter name you chose, and nothing identifying ever leaves your side. Put a customer's email in the meter label and it will be stored, because this service cannot tell the difference. That is a real constraint on you, and pretending otherwise would be the dishonest version of this paragraph.

The meter itself is stricter still, upstream of here. Its metrics never export API keys, tenant identifiers, customer identifiers, methods, or tool names, so the observability path does not reintroduce what the ledger declined to store.

Credentials

Nothing reusable is stored in a form that can be read back.

Your provider keys are sealed

Billing credentials are encrypted with ChaCha20-Poly1305 under a fresh 12 byte nonce per value before they reach a row, in the envelope enc:<base64(nonce||ciphertext)>. A key that is configured but malformed refuses to start the service rather than quietly storing the next credential unprotected.

Tokens are stored as digests

API tokens, tenant API keys and browser sessions are stored as SHA-256 only. A disclosure of the database does not hand over a working credential, and no code path can print one back to you after it is created.

The export client refuses redirects

Outbound calls carrying a billing credential do not follow a 3xx, and destinations are checked against an allowlist. A redirect would carry a credential to a host the allowlist never saw.

Sessions are opaque and revocable

Sign in is passwordless. The cookie is HttpOnly and SameSite=Lax, it is Secure wherever the service is reachable over https, and it is a server side row that can be revoked rather than a self describing token that cannot.

The browser surface

The pages you are reading enforce their own rules.

Every response carries a content security policy with no unsafe-inline and no unsafe-eval, for scripts and for styles. There is not one inline handler or one inline style on this site, which is why the policy can be that strict, and a test renders every page and fails the build if one appears. frame-ancestors 'none' and form-action 'self' close the two holes that matter for a dashboard.

State changing requests are checked against the configured origin, and an absent Origin header is refused rather than assumed friendly. Dashboard pages are served no-store so a shared cache never holds one account's figures.

Auditability

You can read the part that decides what you owe.

The metering rules are not in this service. They are in Apache-2.0 crates published on crates.io, and the classification behaviour is pinned by versioned conformance vectors in plain JSON that a gateway in any language can run. If you think a call was billed that should not have been, that is a claim you can check against source rather than a support ticket you have to win.

Limitations

What this does not do yet.

This is a young service. The following are true today, and they are here because you should decide with them in view rather than discover them later.

  • Single region. One deployment, one database. There is no data residency choice and no multi region failover. An outage here is an outage for everyone, which is why the sidecar is built to keep serving from its last snapshot without us.
  • Subscription status does not gate service. The plane records whether an account is active, past due or canceled, and nothing reads it to refuse service. A canceled account continues to be served. That is deliberate for now, and it is stated because the opposite assumption is the dangerous one.
  • No customer managed encryption keys. The sealing key is held by the service. Sealing protects against a database disclosure, not against the operator.
  • No audit log of human actions yet. Sessions are attributable to a person, and nothing currently records who changed a price or revoked a token. The schema was built to carry it; the recording is not written.
  • No independent security assessment. Nobody outside has audited this. When that changes it will be said here with a date and a name, and not before.

Found something wrong? Mail support@pokitapps.com. Reports about the open source crates belong in the published security policy.
